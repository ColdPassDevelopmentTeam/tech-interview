## 무결성 관련 고려사항

### 무결성 보장 방법

1. 데이터베이스 레벨에서 보장
    1. DBMS가 제공하는 기능을 이용해 데이터의 규칙을 강제하는 가장 강력하고 안정적인 방법
    2. 방법
        1. 제약 조건 설정
            1. 테이블의 열에 특정 규칙을 직접 부여
            2. 잘못된 데이터 입력 원천 차단
            3. 기본 키, 외래 키, 고유 키, Not Null 
        2. 데이터 타입 지정
        3. default 값 지정
        4. 트리거 사용
            1. 데이터 삽입, 수정, 삭제 시 관련된 다른 작업 자동으로 실행시키는 기능
            2. 복잡한 비즈니스 규칙이나 사용자 정의 무결성 구현할 때 사용
        5. stored procedure, 함수 사용
            1. 데이터 입력 전후 검증 로직 추가
        6. 트랜잭션 관리
            1. 작업이 모두 성공하면 데이터를 영구적으로 반영 (commit)
            2. 중간에 하나라도 실패하면 모든 작업을 없던 일로 되돌림 (rollback)
            3. 이렇게 데이터 일관성 보장

1. 애플리케이션 레벨에서 보장
    1. 데이터가 데이터베이스에 도달하기 전 유효성 검증 방법
    2. 사용자와 상호작용하는 프로그램(웹/앱 서버 등)에서 데이터의 유효성을 검증하는 방법
    3. 방법
        1. 유효성 검사
            1. 프로그램 코드 내에서 데이터 확인
        2. 비즈니스 로직 구현
            1. 데이터베이스 제약조건만으로는 표현하기 어려운 복잡한 비즈니스 규칙을 애플리케이션 코드에 구현
        3. 서버 단에서 유효성 검사
            1. spring validation, DTO 검증 등
        4. 프레임워크 기능 사용
            1. JPA의 @NotNull, @Size 등
        5. 프론트엔드 레벨에서 검증
            1. HTML5 input validation (required, pattern, min, max)
            2. JavaScript로 클라이언트 측 검증

### 트랜잭션 성능에 무결성이 미치는 영향

데이터 무결성은 트랜잭션 성능에 **'데이터 신뢰도를 위한 성능 저하'** 라는 직접적인 영향을 미침

데이터의 정확성과 일관성을 강하게 보장할수록 트랜잭션 처리 속도는 느려지는 경향이 있음

<br>

데이터베이스가 모든 데이터 변경 작업(INSERT, UPDATE, DELETE)마다 설정된 무결성 규칙 깨지지 않는지 **검사하는 추가 작업을 수행**하기 때문임

이 검사 과정이 바로 성능에 영향을 미치는 오버헤드

<br>

**성능에 영향 주는 원인들**

- 제약 조건 검사
    - PK, FK, UNIQUE 같은 무결성 제약 조건은 INSERT / UPDATE / DELETE 시마다 검사 필요
        - PK, UNIQUE :
            - 새로운 데이터 삽입하거나 수정할 때, 해당 값이 이미 테이블에 존재하는지 중복 검사 수행
            - 이 검사를 위해 인덱스를 검색하는 과정이 필요
        - FK :
            - 데이터 삽입하거나 수정할 때, 참조하는 부모 테이블에 해당 키가 실제로 존재하는지 확인
            - 이 과정에서 다른 테이블을 조회하는 작업이 추가로 발생하여 지연 생김
    - 트랜잭션 내에서 추가 연산이 발생하여 성능이 저하
- 인덱스 유지 비용
    - PK, UNIQUE, FK 제약 조건은 내부적으로 **인덱스**를 사용
    - 트랜잭션에서 데이터가 추가, 수정, 삭제될 때마다 실제 데이터 변경 + 인덱스 갱신, 정렬 동시에 발생
    - 따라서 쓰기 작업에 대한 비용이 증가
    - 인덱스가 많을수록 트랜잭션 성능 저하
- 락 관리 증가
    - FK 제약 조건 검사 시 부모-자식 테이블 간 데이터 일관성을 보장하려고 락을 더 많이 걸게 됨.
    - 부모 삭제 시 → 자식 레코드 참조 검사 필요 → FK에 인덱스 없으면 테이블 스캔 → 락 오래 유지
    - 동시성 저하, 동시에 여러 트랜잭션이 같은 데이터 변경하지 못함, 대기 시간 증가, 전체 처리량 감소
- 트리거 실행
    - 복잡한 무결성 규칙을 위해 트리거를 사용하는 경우
    - 데이터 변경될 때마다 정해진 코드가 자동 실행
    - 로직 복잡할수록 트랜잭션 성능 저하
    - 트랜잭션마다 추가 SQL 실행되어 성능 저하
